## 1. 使用规则

1. 一个独立问题使用一个 Bug ID：`BUG-UAT-001`、`BUG-UAT-002`……
2. 先记录证据，再决定是否修复；不要因为发现一个 Bug 就自动进行大范围修改。
3. 如果现象可能是业务规则不明确，严重程度先标记为 `P2`，并在备注写 **【需要业务确认】**，不要由 AI 猜测规则。
4. 一个 Bug 修复后必须进入 `RETEST`，由原发现人或项目负责人复测；复测通过后才能 `CLOSED`。
5. 不在台账中保存密码、Token、API Key 或完整身份证件等敏感信息。

## 2. 严重程度

| 等级 | 定义 | 处理原则 |
|---|---|---|
| P0 | 核心流程完全阻断、数据严重错误、越权或无法登录 | 立即停止相关 UAT，优先修复 |
| P1 | 严重功能问题，核心流程可以绕行但影响演示或业务结果 | Baseline 之后优先修复并回归 |
| P2 | 普通功能问题、边界条件或业务规则不明确 | 评估后修复或记录为需求确认 |
| P3 | UI、文字、布局、体验问题，不影响核心业务 | Portfolio Polish 阶段处理 |

## 3. 状态流转

```text
OPEN → IN PROGRESS → FIXED → RETEST → CLOSED
```

- `OPEN`：已发现并记录，尚未开始处理；
- `IN PROGRESS`：已确认修复范围，正在处理；
- `FIXED`：开发者声明已修复，等待复测；
- `RETEST`：正在用原步骤复测；
- `CLOSED`：复测通过并保留证据；
- 如果复测失败，回到 `OPEN`，并补充新的实际结果。

## 7. 修复授权边界

在项目负责人确认 Bug 的严重程度、预期行为和修复范围前：

- 不删除业务数据；
- 不修改数据库 Schema；
- 不扩大权限；
- 不进行无关架构重构；
- 不把“用户觉得不自然”直接改成 AI 猜出的业务规则。
