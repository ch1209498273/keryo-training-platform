# 血透中心医护培训平台

面向血液透析中心医护人员的培训与考核一体化平台。项目代号 `keryo`。

> 它解决的不是"没有课上"，而是**"查的时候说不清"**。

> **仓库分工**：本仓库为脱敏展示快照，只同步 README 与阶段性结论，不再接收代码更新；
> 持续开发在独立私有仓库进行（含完整提交历史、迁移与验收记录）。

---

## 1. 问题

血透是强合规场景。等级评审、医保飞检、院感检查反复问的是同一组问题：

- 这次培训做了吗？谁参加了？
- 学的什么版本的材料？
- 考了多少分？谁判的？
- 这个分数后来被谁改过，依据是什么？

市面上的培训系统大多能回答第一问：有课件、有通知、有完成率。但完成率不是一个可核查的结论，它是一句自我陈述。检查方要的是能逐条回溯的证据链，而多数系统在"谁改过这个分"这一层就已经失守——日志可以被删、改分不留痕、AI 给出的分数直接落库。

这个项目的全部设计取舍，都从"证据链不能断"这个约束出发。

## 2. 产品主张

三条原则写在代码里，不只写在文档里。

**一、可核查优先于可宣称。**
系统输出的每一个结论都要能被第三方逐条回溯。所以审计日志在**数据库层**禁止删除（`BEFORE DELETE` 触发器），"归档"只能是"复制到归档表 + 打标记"，一条都不能少。分数、结论、审批链都带操作人、时间、动作码。

**二、AI 给判断，人担责任。**
AI 可以出题、判分、给学习建议、写督导报告，但任何**对人产生后果**的结论都必须有人按下确认键，且这次确认/覆盖要留痕。AI 的建议分与人工复核分在库里是两列，谁覆盖了谁一目了然。AI 不可用时系统降级为规则清单，而不是假装正常。

**三、边界写进约束，不只写进约定。**
权限、数据范围、可删除性、可申诉次数，都以数据库唯一键、接口断言、状态机条件更新的形式存在。学员"一题一申、一次终审"是三层收口：前端不给入口、接口查任意状态拒绝、唯一键兜住并发。**只挡前端不算数**——接口可以被直调。

## 3. 业务闭环

平台按"培训 → 考核 → 结果 → 改进"四段组织，每段都有对应的证据留痕。

| 环节 | 能力 | 留下的证据 |
|---|---|---|
| 知识准备 | 课件管理、知识点结构化、AI 提取与逐条校验、题库两级审核 | 知识点来源标记、审核人、提案与采纳记录 |
| 培训组织 | 培训计划、场次排课、审批门禁、部门数据范围、签到与学时 | 计划状态机流转、审批人、签到表照片、学时计算依据 |
| 考核实施 | 组卷、计时、防切屏、客观题自动判分、主观题 AI 建议 + 人工复核 | 作答快照、判分依据、AI/人工双评分、异常标记 |
| 结果发布 | 成绩公布、异议申诉与当场改分、一次终审、站内信送达 | 改分前后对照、动作码（手工/覆盖/申诉）、送达与已读 |
| 改进闭环 | 学习建议、薄弱知识点看板、督导报告、应急流程委托 | 建议审计、报告版本、委托触发与撤销记录 |

角色上区分四类运行时身份：系统管理员、总部培训管理者、**中心级管理者**（只看本中心及下级）、学员。中心级不是缩小版管理员——她不能跨中心、不能改计划，但必须能管本中心的场次与考勤。

## 4. AI 的位置

平台有九类 AI 能力：出题、判分建议、结构化提取、答疑、讲义生成、学习建议、督导报告、应急流程图、流程委托。但它们共享同一条纪律：

```
AI 生成 → 结构化落库（标记来源）→ 人工确认/修改 → 留痕 → 才对外生效
```

几个具体的设计选择：

- **答疑不做知识库幻觉兜底。** 回答必须带出处；检索不到依据时明说"没找到"，并记录"无依据"次数进入质量看板，而不是生成一段听起来合理的话。
- **敏感通知必须二次确认。** 涉及不合格、补考、辞退建议这类字眼，AI 只负责起草，发送前必须有人确认（代码判定敏感词，不交给模型判定）。
- **建议有"事实准确率"指标。** 学习建议的评估不只看"有没有收到"，还抽检它对你这段失分的判断是否属实。
- **成本可核算。** 每次调用记录 token 与单价快照，看板读快照而不是现价——单价改了不能篡改历史成本。

```
└────────────────────────┘                 └───────────┬──────────────┘
                                                       │
                              ┌────────────────────────┼────────────────────┐
                              ▼                        ▼                    ▼
                        MySQL 8.4                Redis（会话/菜单缓存）  文件存储 / LLM
```

## 6. 工程实现要点

几个真正花时间、也最能说明工程判断的地方。

**权限三道收敛。** 路由可达性（菜单授权）→ 接口门禁（Shiro 角色/权限断言）→ SQL 数据范围（`DataPermissionHandler` 注入）。前端的隐藏只是体验，不是边界。中心级管理者的部门范围在"计划 / 场次 / 台账"三处口径一致，且**未配置部门时直接报错**，不回落成"看全部"——权限边界来自部门，没有部门就没有边界。

**门禁不能造成死锁。** 计划审批要求"有考试或场次"，但场次属于审批**前**的动作，学员分配又要求计划已激活。若门禁放错位置，会出现"不通过审批不能排场次、不排场次不能通过审批"的死锁，或第二个"不能分学员/不能过审"的循环。业务规则因此被抽成纯函数（`PlanGateRules` / `DeptScopeRules`）并配单测，规则与副作用分离，能单独验证也能单独解释给业务方。

**归档在数据库禁令下完成。** 审计日志表上有禁删触发器，第一次实现"复制→校验→删除"直接报错。改成"复制 + 标记 + 三重校验（标记数 = 应归档数 = 归档表可查数），不一致整体回滚"，实际归档 2414 条，一条未删。

**并发与幂等。** 交卷幂等、状态机用条件更新（`WHERE status = 旧值`）而非先查后改、成绩记录表加唯一键并在冲突时转更新路径。唯一键冲突统一转成人类可读的"该记录已存在"提示，而不是抛 500。

**迁移是手册，不是魔法。** 没有 Flyway，`db/migration/V*.sql` 是版本化执行手册。排序规则不一致（`utf8mb4_general_ci` vs `0900_ai_ci`）会让 JOIN 直接报 `Illegal mix of collations`，这类问题只能在迁移里显式对齐。

## 7. 质量与验证

| 维度 | 当前 |
|---|---|
| 后端单元测试 | **610 个用例 / 63 个测试类，全绿** |
| 前端类型检查 | `vue-tsc --noEmit` 通过 |
| 自动化验收 | 2026-10-18 ~ 10-21 共 7 轮，单轮最大 96 条断言 0 FAIL |
| UI 实操验证 | 6 类角色 69 个叶子页面全量走查 69/69；关键流程 Chromium 实跑留存截图 |
| 缺陷台账 | 累计登记 81 条，按严重度分级，仅 1 条保持 OPEN 并注明原因 |
| 数据迁移 | V1 → V50，逐版可重放 |

验证原则只有一条：**自动化通过不等于业务验收通过**。所以每一轮都分两层记录——脚本断言跑出什么，人在浏览器里实际看到什么。曾经出现过"API 全绿但 UI 建题全量被拒"的情况（前端漏掉一个必填确认框，测试脚本直接调接口绕过了它），这条教训写进了验证手册：**API 造数会绕过前端确认链，API 全绿 ≠ UI 可用**。

## 9. 快速开始

环境：JDK 17、Maven 3.9+、Node.js 20+、MySQL 8.4；Redis 可选。

```bash
# 1. 初始化数据库（按 V1 → V50 顺序执行）
cd yf-bev2-api/src/main/resources/db/migration
mysql -u root -p exam_keryo < V1__keryo_init.sql
# ……依次执行至 V50_audit_archived_flag.sql

# 2. 后端（必须 JDK 17）
export DB_PASSWORD='***' KERYO_JWT_SECRET='<32 位以上随机串>'
export JAVA_HOME=/path/to/jdk-17
mvn -f yf-bev2-api/pom.xml package -DskipTests
java -jar yf-bev2-api/target/yf-bev2-api.jar --server.port=9091

# 3. 前端（开发模式，带 HMR）
cd yf-bev2-vue && npm ci && npm run dev     # http://localhost:5174

# 4. 构建内置静态包（单端口部署，前端由后端 9091 直接提供）
export JAVA_HOME=/path/to/jdk-17
bash scripts/rebuild_frontend.sh
```

访问 `http://localhost:9091`。所有凭据（数据库密码、JWT 密钥、AI Key）只从环境变量读取，源码中不含任何真实凭据；缺失时应用会拒绝启动或按 dev 规则生成一次性密钥。

## 11. 公开边界

本仓库是脱敏后的代码副本，用于工程能力展示。

**为什么拆成两个仓库**：真实项目里的业务口径、机构信息、验收台账与未公开的取舍过程不适合公开；但架构、工程实践与踩坑记录确实值得公开。于是分两处——公开仓库给「能看的结论」，私有仓库放「能追溯的过程」。公开这边只补可脱敏的结论，代码保持快照。

- 本仓库为阶段性快照，代码可能滞后于内部主干；第 7 节的质量数据取自最近一轮内部回归；
- 不含任何真实 API Key、数据库密码、JWT 密钥或私钥；
- 不含真实培训资料、业务数据库导出、运行日志与个人机器路径；
- 不含真实机构名称与人员信息，演示数据均为构造数据；
- 演示账号仅用于本地隔离环境，不得用于任何生产场景；
- 项目来源为真实业务需求，但**未部署于任何医疗机构**，不构成医疗合规结论。

发现疑似凭据泄露时，请先停止传播并轮换凭据，参见 [`SECURITY.md`](SECURITY.md)。
